# Database schema
Migrations (`supabase/migrations`, apply in order): `0001 schema` · `0002 functions_triggers` · `0003 rls_and_grants` · `0004 business_rpc` · `0005 reporting` · `0006 realtime` · `0007 attendance` · `0008 leave` · `0009`/`0010` (attendance gate added, then removed) · `0011 checkin_again` · `0012 attendance_sessions` · `0013 dashboard_home` · `0014 security_hardening` · `0015 message_templates` · `0016 leave_depth` · `0017 attachments` · `0018 finance`.

Tables (RLS on all): profiles, teams, team_memberships, user_targets, pipeline_stages, lost_reasons, lead_sources, services, app_settings, leads, lead_assignments, lead_stage_history, clients, projects, proposals, invoices, payments, activities, tasks, task_comments, daily_reports, coaching_notes, notifications, audit_logs, approval_requests, import_jobs, saved_filters. Views: `user_directory` (id/name/role of active users), `invoice_balances` (security_invoker).

Key rules: UUID PKs; `numeric(14,2)` money; `timestamptz`; business numbers (`LD-000123`, `CL-`, `PR-`, `PP-`, `INV-`) from sequences via `BEFORE INSERT` trigger (preserved if pre-set); `legacy_id` columns for Sheets IDs; `leads.row_version` for optimistic concurrency; `clients.source_lead_id` UNIQUE (no duplicate conversion); CHECKs: lost⇒reason, won⇒client, task completed⇔completed_at, invoice due≥issue, positive amounts; partial unique indexes for open assignment, transaction reference, client request ids (idempotent retries). Payments are never deleted or edited (amount immutable); balance = completed payments − completed refunds; overpayment/over-refund rejected under an invoice row lock. Audit rows are written by triggers (before/after JSON, secret keys stripped) and cannot be updated/deleted/truncated by anyone.

Reporting is database-side (`dashboard_summary`, `report_*`, `target_attainment`, `my_action_items`), SECURITY INVOKER so RLS scopes the numbers. Metric definitions are documented at the top of migration 0005. Estimated pipeline value, won (agreed) value, invoiced and collected are four separate figures.

Attendance (0007): `attendance_records` (one row per user/day, company-timezone `work_date`), `attendance_breaks`, `attendance_corrections` (append-only ledger of requests and admin edits, with reasons). Raw facts only; every derived value (net hours, late/early/overtime minutes, status incl. absent, weekly off, holiday) comes from `attendance_report()` using the `attendance.policy` setting, so UI, CSV and tests agree. With break tracking off the scheduled lunch is deducted only where it overlaps the worked span; with it on, only recorded breaks are — never both. Tables have no write grants: `attendance_check_in/out`, `attendance_break_start/end`, `request_/cancel_/decide_attendance_correction` and `attendance_admin_correct` write using the server clock. Attendance deliberately has no audit triggers (keeps check-in noise out of `audit_logs`). Tests: `supabase/tests/14_attendance.sql`.

Leave (0008): `leave_requests` (full-day, casual/sick/earned/unpaid/other, max 60 days, retro ≤30 days) and view `leave_request_details` (adds working-day count and `can_decide`). Routing is in `app.leave_approvers()`: employee → active mentor(s) of their active teams (admins only if none), mentor → admins; approvers are notified through `app.notify`, as is the applicant on a decision. Approved leave is never copied into attendance: `attendance_report()` derives `on_leave` (holiday/weekly off win; a recorded check-in wins over leave), so cancellations leave no stale rows. Overlapping pending/approved requests are rejected under a per-user advisory lock. Tests: `supabase/tests/15_leave.sql`.

Check in again (0011): the day keeps one `attendance_records` row (first check-in … latest check-out). Checking in after a check-out re-opens it and stores the time away as a closed `attendance_breaks` row with `is_gap = true`; the report deducts gaps (net hours), still judges lateness on the first check-in and early departure on the last check-out, and never deducts lunch twice (with tracking off, gap time already inside the scheduled lunch isn't counted again).

Sessions (0012): `attendance_report()` also returns `sessions` (JSON array of `{in, out}` per check-in/check-out of the day; the open one has `out = null`), shown in the Records table, the "Your day" card and the CSV. A correction collapses the day to a single session and removes that day's gap rows.

Dashboard (0013): `dashboard_home(from, to, scope)` returns `{summary, targets, attendance}` in one call by composing `dashboard_summary`, `target_attainment`, `attendance_report` and `leave_request_details` (nothing is defined twice; SECURITY INVOKER so RLS scopes every number). `attendance` is null for the own view; otherwise today's counts for the people the caller can see plus items awaiting their decision. The page loads the heavy detail (employee/team tables, revenue, growth chart) only when "More details" is opened, and recharts is a separate lazily loaded chunk. Tests: `supabase/tests/17_dashboard_home.sql`.

Security hardening (0014): `app.mfa_ok()` + `app.me()/my_role()/is_admin()/is_mentor()` — a user with a verified TOTP factor only resolves as a person when the JWT is `aal2`, so a password-only session is treated like a deactivated user by every policy and definer function. `can_decide_leave_request()` lets an admin decide an employee's leave after 48 h. `offboard_user(user, receiver)` moves open leads/tasks/client relationships, ends memberships, cancels pending leave and deactivates, in one audited transaction (the server function then bans the auth user). Tests: `18_security_hardening.sql`.

Templates (0015): `message_templates` (email/WhatsApp, `{{contact_name}}`, `{{company_name}}`, `{{owner_name}}`), admin-managed, readable by all active users. Sending opens the user's own mail/WhatsApp app and logs an activity. Leave depth (0016): `leave.quotas` setting (days per year per type), `leave_requests.is_half_day`, `my_leave_balance()`, `request_leave(..., p_half)`; the year of a request is the year of its start date. Tests: `19_leave_depth_templates.sql`.

Attachments (0017): `attachments` rows carry the access rules (lead/client access); the private `attachments` storage bucket (10 MB) only serves/accepts objects with a matching visible row. Tests: `20_attachments.sql`; the storage policies are verified against the hosted project.

Finance (0018, see `docs/finance.md`): `services` gain `description`, `standard_price`, `discount_percent`; `projects` (= deals) snapshot `list_price` + `discount_percent` at creation so catalogue changes never touch agreed prices; `payments.purpose` (advance/partial/final); new tables `invoice_adjustments` (append-only credit/debit, reversed by a mirror row via `reverse_invoice_adjustment()`), `expenses`, `expense_payments`, `salary_obligations`, `salary_payments` — all admin-only RLS, audited, amounts immutable (corrections = cancel a payment / reverse an adjustment, history kept). Admin-gated read model: views `finance_deals`, `finance_invoice_ledger`, `finance_collections`, `client_accounts`, `expense_balances`, `salary_balances` and RPCs `finance_overview`, `finance_series`, `finance_employee_sales` (all period figures come from the single `app.fin_flows()`). `invoice_balances` now includes adjustments (`adjusted_total`, `balance`). Tests: `22_finance.sql`.

# Database schema
Migrations (`supabase/migrations`, apply in order): `0001 schema` · `0002 functions_triggers` · `0003 rls_and_grants` · `0004 business_rpc` · `0005 reporting` · `0006 realtime`.

Tables (RLS on all): profiles, teams, team_memberships, user_targets, pipeline_stages, lost_reasons, lead_sources, services, app_settings, leads, lead_assignments, lead_stage_history, clients, projects, proposals, invoices, payments, activities, tasks, task_comments, daily_reports, coaching_notes, notifications, audit_logs, approval_requests, import_jobs, saved_filters. Views: `user_directory` (id/name/role of active users), `invoice_balances` (security_invoker).

Key rules: UUID PKs; `numeric(14,2)` money; `timestamptz`; business numbers (`LD-000123`, `CL-`, `PR-`, `PP-`, `INV-`) from sequences via `BEFORE INSERT` trigger (preserved if pre-set); `legacy_id` columns for Sheets IDs; `leads.row_version` for optimistic concurrency; `clients.source_lead_id` UNIQUE (no duplicate conversion); CHECKs: lost⇒reason, won⇒client, task completed⇔completed_at, invoice due≥issue, positive amounts; partial unique indexes for open assignment, transaction reference, client request ids (idempotent retries). Payments are never deleted or edited (amount immutable); balance = completed payments − completed refunds; overpayment/over-refund rejected under an invoice row lock. Audit rows are written by triggers (before/after JSON, secret keys stripped) and cannot be updated/deleted/truncated by anyone.

Reporting is database-side (`dashboard_summary`, `report_*`, `target_attainment`, `my_action_items`), SECURITY INVOKER so RLS scopes the numbers. Metric definitions are documented at the top of migration 0005. Estimated pipeline value, won (agreed) value, invoiced and collected are four separate figures.
